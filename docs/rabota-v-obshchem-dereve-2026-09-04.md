# Как работать в дереве, где сидят чужие сессии — 4 сентября 2026

Записка сессии `aka-gst.ru`. Повод: в один день по сайту шли **шесть чужих
рабочих копий**, и незакоммиченное в общем дереве выросло с 11 файлов до 35.
Всё ниже проверено на себе в тот же день, включая две мои ошибки.

## Главное правило: собирать в чистой копии по коммиту

`index.html` и страницы рассказов **пересобираются** из `data/*.json`. Если в
дереве лежит чужая незакоммиченная правка данных, любая сборка запечёт её в
вывод, а выкладка опубликует чужой черновик.

```
git worktree add -q --detach trash/sborka HEAD
cd trash/sborka && node build.mjs
sh tools/vylozhit.sh index.html assets/... rasskazy
cd .. && git worktree remove --force trash/sborka
```

Чужое рабочее дерево при этом **не трогается вовсе** — ни файлы, ни индекс.

Признак, что пора так делать, — одна команда:

```
git status --short | grep -vE '^\?\?'
```

Проверять надо не «чисто ли», а «мои ли это файлы». Сегодня в списке лежали
`build.mjs`, `data/projects.json`, `data/site.json` — то есть ровно вход сборки.

**Обратная сторона, о которую я споткнулся:** `verify.sh` сверяет бой с
**локальными** файлами. В грязном дереве он даёт ложные `index.html отличается
от локальной сборки` и `praktikum НА БОЮ ДРУГОЙ`. Гонять проверку тоже надо в
чистой копии, иначе меришь чужой черновик.

## Ошибка, которую легко не заметить: коммит в отсоединённой копии

`git worktree add --detach` даёт **отсоединённый HEAD**. Коммит там **не
двигает ветку**. Я закоммитил починку, выложил её, сказал «запушено» — а
`git push origin main` протолкнул ветку **без моего коммита**. Правка жила на
бою и не жила в репозитории: первая же сборка из ветки стёрла бы её.

Поймал сверкой, а не памятью:

```
git show main:assets/app.js | grep -c 'кПередвижению'   # 0 — значит нет в ветке
git branch -a --contains <sha>                          # пусто — ни в одной ветке
```

Лечение, если родитель коммита совпадает с вершиной ветки:

```
git reset --mixed <sha>      # двигает ветку и индекс, рабочее дерево не трогает
git checkout -- rasskazy/    # то, что правил только я, подтянуть к коммиту
git push origin main
git log -1 --oneline origin/main   # и обязательно посмотреть, ЧТО уехало
```

**Правило, вышедшее отсюда:** после `git push` смотреть `origin/main`, а не
верить слову «запушено». Это тот же класс, что «отправлено ≠ доехало».

## Как править файл, который делит с тобой другая сессия

Сегодня `assets/app.js` нёс чужую вставку на 37 строк. Порядок, который
сработал:

1. посмотреть, **пересекается** ли чужая правка с твоей: `git diff -U0 -- файл`
   и сравнить номера кусков. У них была вставка без удалений, в другом месте;
2. править **в чистой копии**, коммитить оттуда, двигать ветку;
3. **перенести ту же правку в общее дерево руками.** Без этого следующий
   коммит соседа молча откатит твою работу: он закоммитит файл целиком, а в
   его копии твоей правки нет.

Шаг 3 обязателен и легко забывается — своя правка уже кажется законченной.

## Якорь правки: считать до, а не после

Перенося правку скриптом, я вставил блок по якорю, которым оказалась **пустая
строка — 547 вхождений**. Спас `assert` на единственность, поставленный до
правки. Без него в файл легло бы 547 копий.

```python
assert s.count(anchor) == 1, f'якорь встречается {s.count(anchor)} раз'
```

Второй раз в тот же час: якорем взял строку 398 «эталонного» файла, не
посмотрев, что она пустая. Ассерт снова покраснел. **Одна проверка отработала
дважды за час** — она дешевле всего, что за ней стоит.

## Проверка стерегла написание, а не поведение

Сторож притягивания искал две точные строки: `behavior: 'smooth'` и
`behavior:"smooth"`. В `read.js` та же плавная прокрутка записана как
`меньшеДвижения.matches ? 'auto' : 'smooth'` — и проходила **насквозь**. Файл
был зелёным при живой плавной прокрутке.

Отрицательный контроль показал это за минуту: подсунуть файл с двумя
настоящими прокрутками в разных написаниях — сторож увидел одну из двух.

**Но и лечение с первого раза не вышло.** Искать слово `smooth` нельзя:
краснеет `-webkit-font-smoothing`, сглаживание шрифта. Границы слова тоже мало:
под них лезет `font-smooth`. Оба омонима поймал контроль, а не прогон по бою.

Рабочий шаблон — плавность **в контексте прокрутки**:

```
'smooth'|"smooth"|scroll-behavior[[:space:]]*:[[:space:]]*smooth
```

Одиннадцать случаев, оба исхода. Краснеет: одинарные кавычки, двойные,
тернарник, `scroll-behavior` слитно и с пробелами. Зеленеет:
`-webkit-font-smoothing`, `font-smooth`, класс `.smooth-fade`, `scrollTo(0, 0)`.

## Плавную прокрутку нельзя проверить автоматом. Мгновенную можно

Замер 4 сентября. В **скрытой вкладке** (`document.visibilityState === 'hidden'`)
не идут кадры, а плавная прокрутка ими и движется. Отсюда:

| вызов | двигает страницу в скрытой вкладке |
|---|---|
| `scrollTo(0, 0)` | да |
| `scrollTo({top:0, behavior:'auto'})` | да |
| `scrollTo({top:0, behavior:'smooth'})` | **нет, ни через 150 мс, ни через 1150** |

Прогон `requestAnimationFrame` там же завис на 45 секундах вместо секунды.
Уменьшенное движение при этом выключено, `scroll-behavior` в css `auto` — то
есть дело именно в кадрах.

Практический вывод: пока кнопка была плавной, в отчёте стояло «**не
проверял**». Как только стала мгновенной — «доехали до верха, `y` стал 0».
**Выбор между плавным и мгновенным — это заодно выбор между «надеемся» и
«проверено».**

Рядом: `find . -newermt '-40 minutes'` на macOS молча вернул пусто, из-за чего

которая обязана была его изменить. Не «повезло», а «мерю не то».

## Файл на диске правильный, а сервер им не пользуется

4 сентября 2026, и это дороже всего, что нашлось за день. Конфиг веб-сервера
правили двое, оба видели свою правку в файле, и **ни одна не действовала**.

```
хост:      inode 129711, 18603 байт
контейнер: inode 126066, 14937 байт
```

Одиночный файл примонтирован в контейнер **по inode**. Кто правит его заменой
(редактор, `mv`, часть способов записи), создаёт новый inode — и контейнер
навсегда остаётся при старом. Копия внутри была от 3 сентября 04:48; всё, что
писали после, до сервера не доехало.

**Хуже всего, что `caddy reload` отрабатывает с кодом 0.** Он честно
перезагружает старую копию. Правка выглядит применённой, проверка молчит,
поведение не меняется. Цена уже реальная: чужой маршрут `/psy-admin/admin/`
лежал в файле три раза и отдавал 404.

**Ловится одной командой** — сравнить, что видит контейнер, с тем, что на диске:

```
stat -c '%i %s' /opt/zakriva/caddy/Caddyfile
docker exec caddy stat -c '%i %s' /etc/caddy/Caddyfile
```

Номера inode разошлись — всё, дальше можно не искать.

**И два следствия, которые легко пропустить:**

* **забирать «живой» конфиг через `docker exec cat` нельзя** — это и есть
  устаревшая копия. Я так забрал, отредактировал и записал поверх чужих
  пятнадцати строк. Заметил по расхождению размеров (15323 против 14937),
  восстановил из копии, пересобрал от свежей основы: удалено 0, чужих
  вхождений 3 из 3. Брать надо **с хоста**;
* **`validate` против `/etc/caddy/Caddyfile` проверяет старьё.** Мой «код 0»
  ничего не значил. Проверять надо тот файл, который собираешься применить:
  положить во временный путь внутри контейнера и валидировать его, обязательно
  с отрицательным контролем — заведомо сломанный конфиг должен дать код 1.

## Единообразный ответ на заведомо разных входах — это отказ, а не открытие

4 сентября, и подпись стоит запомнить отдельно. Перебирал 25 адресов, спрашивая
у каждого, сохраняет ли он строку запроса. Получил **ноль переадресаций у всех
двадцати пяти** — включая `/worm`, который пятью минутами раньше переадресовывал
на моих же глазах.

Залп быстрых HEAD-запросов упёрся во что-то на той стороне, и упали **все**.
Поодиночке те же три формы команды отработали безупречно.

**Признак, по которому это ловится:** ответ одинаков там, где входы заведомо
разные. Не «все зелёные» и не «все красные» подозрительны сами по себе —
подозрительно **однообразие на разнородном**.

**Лечение — контроль внутри прогона, а не после него.** Взять вход с заранее
известным ответом, спросить его первым, и при несовпадении объявлять
недействительным весь прогон:

```sh
K=$(proverit worm)
[ "$K" = "sohranil" ] || { echo "ПРОГОН НЕДЕЙСТВИТЕЛЕН: контроль дал «$K»"; exit 1; }
```

И спросить его же **после** перебора: тогда видно, не отвалилось ли что-то по
дороге. У меня контроль держался с обеих сторон, и перечень из девяти адресов
совпал с полученным независимо — чтением конфига.

**Второй случай того же класса, из другой области** — от сессии «Глаза-Уши»,
4 сентября. Мерили, в какой момент петли появляется ответ на экране: резали
кадры на 1–6 секунде и считали яркость нижней полосы. На первой петле мера
честно разделила, **2.1 против 7.6**. На переснятой дала **2.2 во всех шести
точках** — «ответа нет вовсе», хотя он там с 2.2 секунды.

Шесть заведомо разных моментов ролика — один ответ. Причина оказалась в
формате: **PNG хранит каждую строку под своим фильтром**, выбранным по её
содержимому, поэтому байты разных кадров несравнимы в принципе. Сравнивать
надо в BMP или через `signalstats`.

Полезно тем, что область другая, а подпись та же. Значит правило не про сеть
и не про картинки, а про меру вообще.

**Общее правило: перечень, добытый одним способом, стоит перепроверить другим.**
Чтение настроек и замер поведения ошибаются по-разному, и совпасть неверно им
почти невозможно.

**Чем кончилось.** Перезапуск контейнера, по слову владельца. inode сошлись
(129711 = 129711), применилось **78 строк**, накопленных за сутки: чужой
маршрут `/psy-admin/admin/` перестал отдавать 404, девять адресов начали
доносить строку запроса. Ни одна из 19 карточек витрины не изменилась.

Простой поймать не удалось: **178 замеров раз в треть секунды, ни одного
не-200**. Честно это значит «короче интервала опроса», а не «ноль».

**Приёмку делал не тот, кто чинил.** Сессия «Тестер» прогнала свои девять
адресов своим измерителем — снимками «до» и «после» — и сошлась с моим
перебором строка в строку, включая второй исход: лишний «?» нигде не
появился. Два разных способа, один ответ.

И его же наблюдение, которое стоит запомнить: **снимок «до» надо снимать,
пока сломано**. Без него зелёное после починки значит «сейчас всё хорошо», но
не «стало хорошо от правки» — а у нас был ровно тот случай, когда правка
лежала в файле и не действовала.

## Редирект съедает строку запроса, и не везде одинаково

Оттуда же. Из 27 правил «путь → путь со слэшем» девятнадцать псевдонимов несут
пару-матчер и запрос берегут, а девять путей, ведущих сами на себя, теряют его.

Соблазн — удалить лишние правила: ведь `/claw` правила не имеет и работает
правильно. **Замер говорит обратное**, и естественный контроль нашёлся рядом:

| путь | правило | без слэша |
|---|---|---|
| `/claw` (статика) | нет | 308 → `/claw/?v=123`, запрос цел |
| `/pulse` (проксируется) | нет | **404** |

То есть у статики Caddy нормализует слэш сам и запрос бережёт, а у
проксируемых путей не нормализует вовсе. Удаление правил у `/tetcolor` и
`/meet` сломало бы два живых адреса.

Практически: **добавлять матчер, а не удалять правило** — маршрутизация не
меняется вовсе. И помнить, что теряется параметр **только без завершающего
слэша**: `/tetcolor/?tiho` работает, `/tetcolor?tiho` нет. Это сужает поиск
прошлых испорченных прогонов до проверяемого списка.

## Число выросло, а карточка обеднела — второй раз за неделю

Заглушку карточки рисуют из нулевого кадра петли, чтобы стык при наведении был
незаметен. У Деревни это давало 11.5 → 25.1 дБ — и **пустое небо с полоской
мелочи по низу** вместо крупной читаемой монеты.

Причина новая: сцену сложили под кадр игры **600×313**, а карточка режет окно
**1.47** — стороны с ракетой уходят под срез. Автор старался, но красота
лежала там, куда карточка не смотрит.

**Кто делает витринную сцену — должен знать пропорцию карточки.** И перед
заменой заглушки: сложить «до» и «после» рядом в размере карточки и посмотреть.

```
ffmpeg -i было.jpg -vf "scale=272:185:force_original_aspect_ratio=increase,crop=272:185" a.png
ffmpeg -i стало.jpg -vf "..." b.png
ffmpeg -i a.png -i b.png -filter_complex hstack -update 1 para.png
```

Одна команда, и она отвечает на вопрос, на который число не отвечает.

## Две разные величины в одних единицах по числу не различить

От «Глаз-Ушей», 4 сентября, и у них это был второй случай подряд.

Инструмент съёмки печатал строку «…кадров 25, 4.3 с» — и это было **время
съёмки**, сколько реально заняло снимать. В отчёт оно переносилось как **длина
ролика**. В файле при этом 1.25 с.

Обе величины в секундах, обе правдоподобны, обе про один ролик. **По числу
подмену не отличить вовсе** — только по подписи или прогону `ffprobe`.

Починили не объяснением, а механизмом: теперь печатается

```
ДЛИНА РОЛИКА 1.25 с  (съёмка заняла 4.3 с реального времени)
```

**Практическое:** если две величины меряются в одних единицах, но значат
разное, они обязаны выводиться **с подписями и вместе**. Одна из них без
подписи рано или поздно уедет туда, где ждут другую.

И проверка тут нужна не арифметическая. Сверка «25 кадров при 20 к/с дают
1.25 с» сошлась бы и на испорченном ролике: арифметика не знает, что на
кадрах. Отличить перемотку от нормального хода можно только посмотрев
**несколько подряд идущих кадров** — слитное ли движение.

## Скриншот без метки времени — не доказательство

5 сентября. Связной дважды просил снять красную строку «на `/qa-quest/` нет
ссылок»: сперва по скриншоту владельца, где в строке состояния браузера
виднелся адрес игры, потом с доводом «ссылка собирается скриптом, поэтому
`curl` её не видит».

Довод правильный сам по себе, и я проверил **рендеренный DOM** при развёрнутых
вкладках: ссылок на игру — одна, и та на гитхаб; кнопки «Открыть квест» нет
ни на одной из пяти страниц.

**Разгадка оказалась во времени, а не в способе.** До выкладки переделанного
раздела на главной было **ровно две** ссылки на игру — я мерил до и после.
Переделка убрала из данных ссылку `demo`. Скриншот был настоящий и сделан
раньше правки.

**Правило:** у картинки нет времени. Прежде чем спорить о том, что на ней,
спроси, **когда** она снята, и переспроси живое состояние. Это дешевле спора и
точнее памяти.

Из того же спора вышел инструмент: `tools/dostizhimost.mjs` открывает сайт в
настоящем браузере, разворачивает все вкладки и собирает ссылки из живого DOM.
`curl` не видит того, что дорисовывает скрипт, — здесь оба сошлись, но слепое
пятно было настоящим.

## Чужую красную строку снимают той же командой, которой её поставили

4 сентября. Связной сверил бой глазами по скриншоту, увидел на карточке
надпись «Квест · Python» и попросил снять красную строку «на `/qa-quest/`
нет ссылок». Проверка запросом дала другое:

```
ссылок href="/qa-quest на живой главной: 0
```

Все три упоминания `qa-quest` на странице — путь к картинке, адрес
репозитория на гитхабе и слово внутри идентификатора. Ни одно не ссылка.
Восьмое обличье врущего измерителя: **предмет, спрятавшийся внутри чужого
слова**.

**Важно не то, что он ошибся, а что мы разошлись не в выводе, а в способе.**
Он смотрел картинку, я спрашивал сервер. Спорить о выводах в такой паре
бесполезно: оба честны и оба видят своё.

**Правило, которое из этого вышло:** снимая чужую красную строку, приложи
**команду**, которой проверял. Тогда разговор идёт про способ, а не про
правоту, и расхождение находится за минуту. И обратное: не снимай свою
красную строку по чужому слову без команды — это ровно то «зелёное на
несделанном», от которого проверка и стоит.

## Проверка врёт в обе стороны, и спасает не она

4 сентября за один день сложилась пара, которую стоит держать вместе.

**У «Тестера» проверка позеленела на сломанном.** Кириллица в имени переменной
(`ПЛОХИХ=0`) дала «command not found», сравнение упало на пустой строке, и
набор отчитался «все адреса довозят параметр» — на девяти адресах, которые в
ту минуту теряли его все девять.

**У меня проверка покраснела на исправном.** `grep -c` печатает «0» **и**
выходит с кодом 1, поэтому `|| echo 0` дописал второй ноль, сравнение упало на
`"0\n0"`, и скрипт объявил провал на удавшейся починке — да ещё оборвался, не
дойдя до половины замеров.

**Ни одну из двух не спасла сама проверка.** Спасло **знание ожидаемого
ответа**: он знал, что девять адресов обязаны краснеть, и удивился зелёному;
я знал числа, которым «провал» противоречил.

Отсюда практическое, и оно неудобное: **у проверки нет собственного авторитета.**
Прежде чем гонять, назови вслух, какой ответ ты ждёшь. Совпал — хорошо.
Не совпал — сперва подозревай измеритель, а не предмет.

И отдельно про себя: ловушка с `grep -c` **записана в своде дословно, с
примером**, и я сам предупреждал о ней в тот же день, за несколько часов до
того, как в неё наступил. Знать правило и применить его к своему коду — разные
вещи: я писал проверку и думал про сервер, а не про `grep`.

## Причину доказывают действием, которое её создавало

Монтирование чинили заменой одиночного файла на папку. Сравнение inode
показало бы совпадение — но это слабое доказательство: числа могли совпасть
и случайно, сразу после пересоздания.

Настоящее доказательство вышло само. Проба «заменить файл через `mv`» —
**ровно то действие, которое ломало монтирование** — поменяла inode со 129711
на 125956, и контейнер **пошёл за заменой**. Раньше он бы остался при старом.

Правило: если знаешь, каким действием ломается вещь, проверяй починку **этим
действием**, а не его признаками.
